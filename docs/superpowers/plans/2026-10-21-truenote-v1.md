# truenote v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build truenote v1, an installable offline guitar tuner web app for iPhone and Android. It detects the played string automatically, shows it on a 3 + 3 headstock with an arc needle, and plays a ding when the string is in tune.

**Architecture:**
- **Shape:** a single-page React app in one feature folder, `src/features/tuner/`, with three layers:
  - `core` is pure TypeScript. It holds pitch detection (YIN), the note maths, the nearest string and the in-tune rule.
  - `audio` is the browser bridge: microphone, Web Audio, wake lock, lifecycle and the ding. It exposes a small engine.
  - `ui` holds the React components and `useTuner`, which receives the engine.
- **Composition:** `src/app/` composes the feature and registers the service worker.
- **Hosting:** the app is served as static assets by a Cloudflare Worker, built by Workers Builds from GitHub.

**Tech Stack:**
- **App:** Node 24.18.0, pnpm 11.28.6, TypeScript 6.0.3, React 19.3.1, Vite 8.3.4, Tailwind CSS 4.3.3.
- **Quality:** Oxlint 1.89.0 (type-aware) and Prettier 3.9.10.
- **Tests:** Vitest 5.0.5, jsdom 30.1.3 and Testing Library.
- **Hooks:** Husky 9.1.7, lint-staged 17.6.0 and commitlint 21.2.4.
- **Delivery:** vite-plugin-pwa 2.0.0, wrangler 4.151.3 and GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-21-truenote-tuner-design.md` (approved 2026-10-21). Read it alongside this plan.

## Global Constraints

Every task implicitly includes these:

**Versions and pins**
- **Node:** `24.18.0` in `.nvmrc`, with `"engines": { "node": "^24.18.0" }`.
- **pnpm:** `"packageManager": "pnpm@11.28.6+sha512.55d90390c3b39042f1505a2697789f0256c6d95bb28bdd7cb731af1887c9f2629ef581acb9f4e4ec772024c8203c2aed22a03299b97103fdcf32668e905d0024"`. pnpm 12 is not used.
- **pnpm settings:** they live only in `pnpm-workspace.yaml`; `.npmrc` and environment variables are ignored by pnpm 11.
  - `minimumReleaseAge: 1440` is kept on.
  - Packages with install scripts are listed under `allowBuilds:` with an explicit `true`/`false`, and `false` unless the build is needed. `onlyBuiltDependencies` is silently ignored by pnpm 11, so it is never used.
- **New dependencies:** they are added with an exact version (`pnpm add -D name@x.y.z`). Versions published less than a day ago are refused by pnpm; that is intended.

**Language and naming**
- **English everywhere in the repository:** code, comments, docs, commit messages, PR descriptions and UI copy. The conversation with the owner is in Spanish.
- **Files and folders:** kebab-case, including components (`needle-meter.tsx`) and hooks (`use-tuner.ts`). Components and types are PascalCase. Module constants are UPPER_SNAKE_CASE with units (`IN_TUNE_HOLD_MS`). Booleans read as questions (`isInTune`).

**Code conventions**
- **Exports:** named exports only; config files are the exception.
- **String values:** no `enum`. They are `as const` objects with derived types, and code compares against `TUNER_STATUS.LISTENING`, never `'listening'`.
- **No magic numbers.** Only `0`, `1` and `-1` are allowed inline. Literals such as `2`, `0.5` or `1200` inside expressions need a named constant. Module-level `const X = 5` and `as const` objects are fine.
- **Layer rules (spec §6.2).**
  - Imports inside a feature are relative, so no `@/` alias is used.
  - `core` imports no React and no browser globals. `audio` imports no `ui` and no React. Features never import each other, and `shared/` (empty in v1) never imports features.
  - Oxlint enforces all of this.
- **Imports are extensionless.** Types use `import type` (`verbatimModuleSyntax`).

**Formatting and styling**
- **Prettier:** default settings plus the Tailwind plugin, so semicolons and double quotes. Snippets in this plan omit semicolons for brevity, and Prettier adds them.
- **Tailwind:**
  - Classes use theme tokens only, with no arbitrary values such as `w-[37px]` or `text-[#3f3]`.
  - Class strings outside a JSX `className` go through `tw\`…\`` or `clsx(…)` so they are linted and sorted.
  - The needle angle is written to the `--needle-angle` CSS variable through a ref, never through React state or the `style` prop.

**Tests and commits**
- **Tests:** they sit next to the file they test. `core` tests run in the `node` environment and everything else in `jsdom`. Coverage must be at least 80 % for lines, branches, functions and statements.
- **Commits:** Conventional Commits, `type(scope): subject`, with an English subject that starts lowercase. Proper nouns keep their case (PWA, iOS, React, `useTuner`).

**Product rules (from the spec)**
- **In-tune rule:** `IN_TUNE_TOLERANCE_CENTS = 5`, `OUT_OF_TUNE_THRESHOLD_CENTS = 8`, `IN_TUNE_HOLD_MS = 500`, `PITCH_HOLD_MS = 1500`, and a meter range of ±50 cents.
- **Fixed copy:** `truenote`, `Standard · E A D G B E`, `Tap to start`, `tune up` / `tune down`, `In tune ✓`, and `–` (en dash) for "no note".
- **iOS audio:** the `AudioContext` is created and resumed inside the tap handler before any `await`. The microphone is requested with `echoCancellation`, `noiseSuppression` and `autoGainControl` all `false`. The page never reloads or navigates by itself while listening, so service-worker updates only ever prompt.
- **No backend:** no analytics, no tracking.

**Owner-only steps.** These need the owner's own accounts, so Claude does them only after the owner confirms each one:
- creating the GitHub repository and the first push
- any change to GitHub settings
- connecting Cloudflare Workers Builds and setting its variables
- merging a PR (unless the owner explicitly asks Claude to merge)

## Review Focus

These are inputs the spec implies but no task's tests would otherwise exercise. Each one has a test in its owning task, marked "(Review Focus)" there.

1. **Double tap or backgrounding while the permission prompt is open.** "Tap to start" tapped twice quickly, or the app hidden during the prompt, must leave exactly one microphone stream, or none. A stream that arrives after `stop()` is released at once (Tasks 16 and 17).
2. **Android input.** Microphones at 44.1 kHz, or with a DC offset, must still read within ±1 cent (Task 11).
3. **Low E on a phone mic.** A weak fundamental under a louder 2nd harmonic must read as the fundamental, not an octave up (Task 11).
4. **Switching strings.** Playing a different string while the previous one is still ringing in tune must move to the new string and restart the in-tune hold, with no stale green (Task 14).
5. **Very detuned strings.** For offsets beyond ±50 cents, the needle stays pinned at the edge while the text shows the true value, for example `+73 cents · tune down` (Tasks 12, 14, 20 and 21).

## How every task ships

Each task is one branch and one pull request, following spec §8.2–8.4:

1. **Explain in Spanish first.** Before touching anything, Claude explains to the owner what the task does and why.
2. **Start from an up-to-date `main`:** `git switch main && git pull --rebase && git switch -c <branch>`, using the branch name given in the task.
3. **Work the steps.** Commit exactly as listed, small and in order. From Task 7 on, the hooks run on every commit and push. Never bypass them with `--no-verify`.

4. **Final gate.** Run every check that exists at that point (`pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm test:coverage`, `pnpm build`). All must exit 0.

6. **The owner reviews.** That includes CI (from Task 8) and the Cloudflare preview URL on the iPhone when the task changes the app (from Task 10). The owner then merges with **Rebase and merge**. Claude runs `gh pr merge <number> --rebase` only when asked.
7. **Back to `main`:** `git switch main && git pull --rebase`.

- [ ] **Step 3: Implement `analyzePitch` and `detectPitch` in `detect-pitch.ts` with YIN.** This is the one algorithm the tests do not pin down. It was prototyped on 2026-10-21 and measured at a worst case of 0.03 cents over this whole test set at 44.1 and 48 kHz with 2048 samples, about 0.8 ms per frame. Let `N = samples.length`:
  1. Compute the mean and the mean-removed RMS. If `rms < MIN_RMS_LEVEL`, return `{ frequencyHz: null, clarity: 0, rmsLevel: rms }`.
  2. Set `τmin = floor(sr / MAX_FREQUENCY_HZ)`, `τmax = min(ceil(sr / MIN_FREQUENCY_HZ), floor(N / 2))`, and window `W = N − τmax`.
  3. Compute the difference function `d(τ) = Σ_{j<W} (x[j] − x[j+τ])²` for `τ = 1…τmax+1`.
  4. Compute the cumulative mean normalized difference: `d′(0) = 1`, `d′(τ) = d(τ)·τ / Σ_{k=1..τ} d(k)` (1 when the sum is 0).
  5. Find the first `τ ≥ τmin` with `d′(τ) < YIN_THRESHOLD`, then walk forward while `d′` keeps falling. If there is none, return null with clarity 0.
  6. Refine `τ` with parabolic interpolation on the **raw `d`**, not on `d′`. The prototype measured 0.03 c worst with `d` and 0.08 c with `d′`. Use `τ̂ = τ + (d[τ−1] − d[τ+1]) / (2·(d[τ−1] − 2d[τ] + d[τ+1]))`, or `τ` when the denominator is 0.
  7. Return `frequencyHz = sr / τ̂` and `clarity = 1 − d′(τ)`.

Branch `feat/core-tuning-state`.

**Files:** Create `src/features/tuner/core/tuning-state.ts` and its `.test.ts`; modify `constants.ts`.

**Interfaces:**

- Produces:
  ```ts
  // constants.ts (add)
  export const IN_TUNE_TOLERANCE_CENTS = 5
  export const OUT_OF_TUNE_THRESHOLD_CENTS = 8
  export const IN_TUNE_HOLD_MS = 500
  export const PITCH_HOLD_MS = 1500
  export const PITCH_LOST_MS = 200 // a gap this long means the string was plucked again
  // tuning-state.ts
  export type TuningReading = { string: GuitarString; offsetCents: number; isInTune: boolean }
  export type TuningState = { reading: TuningReading | null; inBandSinceMs: number | null; lastPitchAtMs: number | null; shouldPlayDing: boolean }
  export const INITIAL_TUNING_STATE: TuningState
  export function updateTuningState(state: TuningState, frequencyHz: number | null, nowMs: number): TuningState
  ```

The rules come from spec §4.4. They are written out here because the tests alone do not fix the order of the checks:
- **`frequencyHz === null`:** if `lastPitchAtMs !== null` and `nowMs − lastPitchAtMs ≥ PITCH_HOLD_MS`, return `INITIAL_TUNING_STATE`. Otherwise keep the state as it is, with `shouldPlayDing: false`.
- **A pitch:** let `match = findNearestString(frequencyHz)`. It is a **new pluck** when there was no previous pitch, when `nowMs − lastPitchAtMs ≥ PITCH_LOST_MS`, or when `match.string.id` differs from the shown string. On a new pluck `wasInTune = false` and `inBandSinceMs = null`. Otherwise both carry over.
  - **If `wasInTune`:** it stays in tune unless `|offset| > OUT_OF_TUNE_THRESHOLD_CENTS`. In that case it is not in tune and `inBandSinceMs = null`.
  - **Otherwise:** if `|offset| ≤ IN_TUNE_TOLERANCE_CENTS`, set `inBandSinceMs ??= nowMs` and make it in tune once `nowMs − inBandSinceMs ≥ IN_TUNE_HOLD_MS`. If the offset is outside the tolerance, set `inBandSinceMs = null`.
  - `shouldPlayDing = isInTune && !wasInTune`, which is true on exactly one update. Every path out of in-tune re-arms the ding, so no separate "armed" flag is needed.
  - `lastPitchAtMs = nowMs`.

- [ ] **Step 1: Write the failing tests.** Use a helper `feed(state, frequencyHz, fromMs, toMs)` that applies one update every 16 ms. Unless a test says otherwise, A2 at +3 cents is "in band".

  2. `enters in tune after 500 ms within ±5 cents`: not in tune at 496 ms; in tune with `shouldPlayDing` at 512 ms; `shouldPlayDing` false at 528 ms.
  3. `restarts the hold when the offset leaves ±5 cents`: in band 0–304 ms, +6 cents at 320 ms, in band again from 336 ms. Not in tune at 800 ms, in tune by 900 ms.
  4. `stays in tune up to ±8 cents and leaves beyond it`: once in tune, +7 cents keeps it in tune and +9 cents leaves.
  5. `plays the ding again after leaving and re-entering`.
  6. `never repeats the ding while the string keeps sounding in tune`: 0–3000 ms in band gives exactly one update with `shouldPlayDing`.
  7. `keeps the last reading for 1.5 s after the pitch is lost`: last pitch at 600 ms. At 2099 ms the reading is still shown and in tune; at 2100 ms the state equals `INITIAL_TUNING_STATE`.
  8. `treats a pitch after 200 ms of silence as a new pluck`: in tune, nulls for 200 ms, then in band. It is not in tune at first and dings again after 500 ms.
  9. `ignores dropouts shorter than 200 ms`: in tune, nulls for 100 ms, then in band. Still in tune, no ding.
  10. `resets when another string is played`: in tune on A, then low E at +2 cents. The reading is `low-e` and not in tune; after 500 ms it is in tune and dings.

**Behaviour:**
- **`start()`:**

  - If audio is unsupported, the status becomes `error` / `unsupported`.

  2. `analyzePitch` with `context.sampleRate`.

  4. `updateTuningState`.
  5. Publish a new snapshot.
